# Contributing to NoisePlace

Спасибо за участие в разработке NoisePlace!

Этот документ описывает основные правила совместной работы над проектом.

## 1. Основные принципы

- `main` — основная стабильная ветка проекта.
- Новые функции и исправления разрабатываются в отдельных ветках.
- Изменения попадают в `main` через Pull Request.
- Каждый PR должен пройти проверку CI и Code Review второго разработчика.
- Не отправляйте незавершённые изменения напрямую в `main`.

## 2. Работа с ветками

Для каждой задачи создавайте отдельную ветку от актуального `main`.

Используем следующие префиксы:

| Префикс | Назначение | Пример |
|---|---|---|
| `feature/` | Новая функциональность | `feature/user-profile` |
| `fix/` | Исправление ошибки | `fix/artist-search` |
| `refactor/` | Рефакторинг | `refactor/auth-handler` |
| `chore/` | Инфраструктура и обслуживание | `chore/github-actions-ci` |

Пример создания ветки:

```bash
git checkout main
git pull origin main
git checkout -b feature/user-profile
```

Старайтесь решать одну логически связанную задачу в одной ветке.

## 3. Коммиты

Используйте короткие и понятные сообщения коммитов.

Рекомендуемый формат:

```text
type: краткое описание изменений
```

Основные типы:

- `feat` — новая функциональность.
- `fix` — исправление ошибки.
- `refactor` — изменение структуры кода без изменения поведения.
- `test` — добавление или изменение тестов.
- `docs` — документация.
- `chore` — технические и инфраструктурные изменения.

Примеры:

```text
feat: add user profile endpoint
fix: handle empty artist search query
test: add release handler tests
docs: add contributing guidelines
chore: add GitHub Actions workflow
```

Коммиты должны отражать логически завершённые изменения.

## 4. Pull Requests

Когда задача готова:

1. Убедитесь, что локальные проверки проходят.
2. Отправьте ветку в GitHub.
3. Создайте Pull Request в `main`.
4. Заполните описание PR по шаблону.
5. Дождитесь проверки CI.
6. Передайте PR на Code Review второму разработчику.
7. После одобрения и успешных проверок выполните Merge.

### Code Review

Для каждого PR требуется ревью второго разработчика.

При проверке обращайте внимание на:

- Корректность реализации.
- Возможные ошибки и граничные случаи.
- Обработку ошибок.
- Безопасность и работу с пользовательскими данными.
- Совместимость API.
- Изменения схемы базы данных.
- Наличие необходимых тестов.

Если есть замечания, оставляйте комментарии непосредственно к соответствующим строкам кода.

Автор PR должен исправить замечания или обсудить предложенные альтернативы.

Обязательное взаимное ревью является командным правилом. GitHub Free для текущего приватного репозитория не обеспечивает его техническое принудительное применение.

## 5. Локальные проверки

Перед созданием PR выполните:

```bash
go test -race ./...
go vet ./...
```

Обе команды должны завершиться без ошибок.

Также проверьте работу изменённого функционала вручную, если это необходимо.

Инструкции по запуску приложения и локального окружения приведены в `README.md`.

## 6. Работа с базой данных

При изменении схемы PostgreSQL:

- Добавляйте миграции, а не изменяйте уже применённые миграции.
- Сохраняйте согласованность парных миграций `up` и `down`.
- Учитывайте существующие данные при изменении таблиц и ограничений.
- Проверяйте, что миграции корректно применяются и откатываются.

При изменении SQL-запросов:

- Обновляйте соответствующие запросы в `db/queries/`.
- После изменений генерируйте код с помощью `sqlc generate`.
- Не редактируйте сгенерированные sqlc-файлы вручную.
- Проверяйте, что сгенерированный код соответствует SQL-запросам.

## 7. Общие правила разработки

- Следуйте существующей структуре проекта.
- Используйте стандартный формат Go (`gofmt`).
- Старайтесь не усложнять реализацию без необходимости.
- Обрабатывайте ошибки явно.
- Не добавляйте секреты и пароли в репозиторий.
- Не включайте в коммиты локальные конфигурации и временные файлы.
- Добавляйте тесты для новой функциональности и исправлений ошибок.

## 8. Завершение работы

После успешного ревью и прохождения CI PR можно слить в `main`.

После Merge удалите использованную feature- или fix-ветку, если она больше не нужна.

Спасибо за вклад в NoisePlace!
