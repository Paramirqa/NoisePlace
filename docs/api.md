NoisePlace API

1. Общая информация

NoisePlace — музыкальная платформа для каталогизации исполнителей и релизов, создания личных коллекций и обмена музыкальными рекомендациями.

Backend реализован на Go. Данные хранятся в PostgreSQL. SQL-запросы генерируются с помощью sqlc.

Базовый URL

При локальном запуске:

http://localhost:8080

Версионированные endpoint’ы располагаются по пути /api/v1.

Формат обмена данными

* Формат запросов: JSON.
* Формат ответов: JSON.
* Кодировка: UTF-8.
* Заголовок запросов с JSON-телом: Content-Type: application/json.

2. Служебные endpoint’ы

GET /healthz

Проверяет, отвечает ли HTTP-сервер.

Успешный ответ — 200 OK:

{
  "status": "ok"
}

Этот endpoint не проверяет доступность PostgreSQL.

GET /readyz

Проверяет готовность приложения принимать запросы, выполняя проверку подключения к PostgreSQL.

Успешный ответ — 200 OK:

{
  "status": "ready"
}

Если база данных недоступна, возвращается 503 Service Unavailable:

{
  "status": "not_ready"
}

3. Исполнители

Базовый путь:

/api/v1/artists

3.1. Создание исполнителя

POST /api/v1/artists

Создаёт запись об исполнителе в каталоге.

Тело запроса

Поле	Тип	Обязательное	Описание
name	string	Да	Отображаемое имя исполнителя
normalized_name	string	Нет*	Нормализованное имя для поиска
sort_name	string или null	Нет	Имя для сортировки
description	string или null	Нет	Описание исполнителя
image_url	string или null	Нет	URL изображения

* Если normalized_name не передан или пустой, приложение формирует его из name, удаляя пробелы по краям и приводя строку к нижнему регистру.

name не должен быть пустым или состоять только из пробелов.

Пример запроса

curl -i -X POST http://localhost:8080/api/v1/artists \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "ATL",
    "normalized_name": "atl",
    "sort_name": "ATL",
    "description": "Российский рэп-исполнитель",
    "image_url": null
  }'

Успешный ответ

HTTP 201 Created:

{
  "id": 1,
  "name": "ATL",
  "normalized_name": "atl",
  "sort_name": "ATL",
  "description": "Российский рэп-исполнитель",
  "image_url": null,
  "created_at": "2026-10-22T15:24:50.00634Z",
  "updated_at": "2026-10-22T15:24:50.00634Z"
}

id и временные метки формируются базой данных.

Возможные ошибки

HTTP-код	Причина
400 Bad Request	Некорректный JSON, неизвестное поле или отсутствует обязательное имя
500 Internal Server Error	Ошибка при сохранении записи

⸻

3.2. Получение исполнителя по ID

GET /api/v1/artists/{id}

Возвращает информацию об исполнителе по его идентификатору.

Параметры пути

Параметр	Тип	Описание
id	integer	Положительный идентификатор исполнителя

Пример запроса

curl -i http://localhost:8080/api/v1/artists/1

Успешный ответ

HTTP 200 OK.

Возвращается объект исполнителя с полями, перечисленными в разделе создания.

Возможные ошибки

HTTP-код	Причина
400 Bad Request	ID некорректен или не является положительным числом
404 Not Found	Исполнитель не найден
500 Internal Server Error	Ошибка базы данных

Пример ответа при отсутствии записи:

{
  "error": "artist not found"
}

⸻

3.3. Поиск исполнителей

GET /api/v1/artists

Выполняет поиск по нормализованному имени исполнителя.

Query-параметры

Параметр	Тип	Обязательный	По умолчанию	Ограничения
query	string	Да	—	Не должен быть пустым
limit	integer	Нет	20	От 1 до 100
offset	integer	Нет	0	Неотрицательное число

Поиск использует частичное совпадение с normalized_name.

Текущая реализация SQL использует LIKE, поэтому поиск чувствителен к регистру. Для предсказуемых результатов следует передавать поисковую строку в нижнем регистре.

Результаты сортируются по normalized_name, затем по id.

Пример запроса

curl -i 'http://localhost:8080/api/v1/artists?query=atl&limit=20&offset=0'

Успешный ответ

HTTP 200 OK.

Возвращается JSON-массив исполнителей:

[
  {
    "id": 1,
    "name": "ATL",
    "normalized_name": "atl",
    "sort_name": "ATL",
    "description": "Российский рэп-исполнитель",
    "image_url": null,
    "created_at": "2026-10-22T15:24:50.00634Z",
    "updated_at": "2026-10-22T15:24:50.00634Z"
  }
]

Если совпадений нет, возвращается пустой массив:

[]

Пример пагинации

Первая страница:

GET /api/v1/artists?query=atl&limit=20&offset=0

Следующая страница:

GET /api/v1/artists?query=atl&limit=20&offset=20

Возможные ошибки

HTTP-код	Причина
400 Bad Request	Не указан query, некорректный limit или offset
500 Internal Server Error	Ошибка базы данных

Пример ответа при отсутствии поискового параметра:

{
  "error": "query parameter is required"
}

⸻

3.4. Обновление исполнителя

PUT /api/v1/artists/{id}

Обновляет данные существующего исполнителя.

Тело запроса

Используются те же поля, что и при создании:

* name;
* normalized_name;
* sort_name;
* description;
* image_url.

name обязателен и не может быть пустым.

Если normalized_name не передан или пустой, приложение формирует его из name.

Важно: PUT обновляет все редактируемые поля, а не только переданные. Если необязательное поле отсутствует, оно будет сброшено в NULL. Для частичного обновления в будущем можно добавить PATCH.

Пример запроса

curl -i -X PUT http://localhost:8080/api/v1/artists/1 \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "ATL",
    "normalized_name": "atl",
    "sort_name": "ATL",
    "description": "Российский рэп-исполнитель, автор песен",
    "image_url": null
  }'

Успешный ответ

HTTP 200 OK.

Возвращается обновлённый объект исполнителя. Поле updated_at должно отражать время обновления.

Возможные ошибки

HTTP-код	Причина
400 Bad Request	Некорректный ID или тело запроса
404 Not Found	Исполнитель не найден
500 Internal Server Error	Ошибка базы данных

4. Формат ошибок

Для обработанных ошибок API возвращает JSON-объект с полем error.

Пример:

{
  "error": "artist not found"
}

Коды 4xx означают ошибку запроса или отсутствие ресурса. Код 500 означает внутреннюю ошибку приложения.

В ответах 500 подробности внутренней ошибки не раскрываются клиенту.

5. Ограничения текущей версии

На текущем этапе:

* каталог исполнителей не требует авторизации;
* проверка дубликатов по имени на уровне API не реализована;
* поиск работает по normalized_name;
* регистрация пользователей и управление личными библиотеками пока не входят в реализованный API;
* каталог релизов и связи исполнителей с релизами ещё не имеют HTTP endpoint’ов;
* формат ошибок пока не унифицирован отдельным middleware;
* автоматическая OpenAPI-спецификация пока отсутствует.

Документация описывает реализованное поведение и должна обновляться вместе с изменениями API.
