Структура базы данных

## 1. Общая информация

Проект использует PostgreSQL для хранения музыкального каталога.

Работа с базой данных организована следующим образом:

* PostgreSQL — основная СУБД.
* golang-migrate — управление миграциями схемы базы данных.
* sqlc — генерация Go-кода на основе SQL-запросов.
* pgx/v5 — подключение к PostgreSQL и выполнение запросов.

Основные директории:

db/
├── migrations/       # SQL-миграции
└── queries/          # SQL-запросы для sqlc
internal/
└── database/
    ├── postgres.go   # Подключение к PostgreSQL
    └── sqlc/         # Сгенерированный sqlc-код

Важно: файлы в internal/database/sqlc/ генерируются автоматически. Изменения в запросах нужно вносить в db/queries/, а изменения схемы — через миграции.

## 2. Таблицы

### `artists`

Хранит исполнителей музыкального каталога.

Основные поля:
- `id` — первичный ключ;
- `name` — отображаемое имя;
- `normalized_name` — нормализованное имя для поиска;
- `sort_name` — имя для сортировки;
- `description` — описание;
- `image_url` — ссылка на изображение;
- `created_at`, `updated_at` — временные метки.

Ограничения:
- `name` и `normalized_name` не могут быть пустыми после `TRIM`.

Индекс:
- `idx_artists_normalized_name` — по `normalized_name`.

### `releases`

Хранит музыкальные релизы.

Основные поля:
- `id` — первичный ключ;
- `title` — название;
- `release_type` — тип релиза;
- `release_date` — дата выхода;
- `description` — описание;
- `cover_url` — ссылка на обложку;
- `created_at`, `updated_at` — временные метки.

Допустимые типы релиза: `album`, `ep`, `single`, `compilation`, `mixtape`, `live`, `other`.

Ограничения:
- `title` не может быть пустым после `TRIM`;
- `release_type` должен входить в список допустимых типов.

Индексы:
- `idx_releases_title` — по `title`;
- `idx_releases_release_date` — по `release_date`.

### `release_artists`

Связывает релизы с исполнителями.

Поля:
- `release_id` — идентификатор релиза;
- `artist_id` — идентификатор исполнителя;
- `role` — роль исполнителя;
- `position` — позиция для упорядочивания.

Допустимые роли: `primary`, `featured`, `producer`. По умолчанию используются роль `primary` и позиция `0`.

Первичный ключ: `(release_id, artist_id)`. Поэтому один исполнитель может иметь только одну роль в рамках одного релиза.

Ограничения и связи:
- удаление релиза удаляет связанные записи;
- удаление исполнителя запрещено, пока существуют связанные релизы;
- `position` не может быть отрицательным.

Индекс:
- `idx_release_artists_artist_release` — по `(artist_id, release_id)`.

Миграция `000002_unique_release_artist` удаляет дублирующиеся связи и меняет первичный ключ с `(release_id, artist_id, role)` на `(release_id, artist_id)`.

### `artist_external_ids`

Хранит внешние идентификаторы исполнителей.

Поля:
- `id` — первичный ключ;
- `artist_id` — исполнитель;
- `source` — источник идентификатора;
- `external_id` — идентификатор во внешней системе;
- `created_at` — время создания записи.

Ограничения:
- `source` и `external_id` не могут быть пустыми после `TRIM`;
- пара `(source, external_id)` уникальна;
- пара `(artist_id, source)` уникальна;
- при удалении исполнителя его внешние идентификаторы удаляются.

### `release_external_ids`

Хранит внешние идентификаторы релизов.

Поля аналогичны `artist_external_ids`, но вместо `artist_id` используется `release_id`.

Ограничения:
- `source` и `external_id` не могут быть пустыми после `TRIM`;
- пара `(source, external_id)` уникальна;
- пара `(release_id, source)` уникальна;
- при удалении релиза его внешние идентификаторы удаляются.

### `users`

Хранит учётные записи пользователей.

Поля:
- `id` — первичный ключ;
- `username` — имя пользователя;
- `email` — адрес электронной почты;
- `password_hash` — хеш пароля;
- `created_at`, `updated_at` — временные метки.

Ограничения:
- имя пользователя, email и хеш пароля не могут быть пустыми после `TRIM`;
- `username` уникален;
- `email` уникален.

### `user_library_artists`

Хранит исполнителей, добавленных пользователями в личную библиотеку.

Поля:
- `user_id` — пользователь;
- `artist_id` — исполнитель;
- `added_at` — время добавления.

Первичный ключ: `(user_id, artist_id)`, поэтому исполнитель не может быть добавлен в библиотеку одного пользователя повторно.

При удалении пользователя или исполнителя соответствующая запись библиотеки удаляется.

Индекс:
- `idx_user_library_artists_artist_id` — по `artist_id`.

### `user_library_releases`

Хранит релизы, добавленные пользователями в личную библиотеку.

Поля:
- `user_id` — пользователь;
- `release_id` — релиз;
- `added_at` — время добавления.

Первичный ключ: `(user_id, release_id)`.

При удалении пользователя или релиза соответствующая запись библиотеки удаляется.

Индекс:
- `idx_user_library_releases_release_id` — по `release_id`.

## 3. Миграции

Структура базы данных изменяется миграциями из `db/migrations`.

- `000001_init` — создаёт музыкальный каталог, связи релизов с исполнителями и таблицы внешних идентификаторов.
- `000002_unique_release_artist` — удаляет дублирующиеся связи исполнителей с релизами и меняет первичный ключ `release_artists`.
- `000003_create_users` — создаёт таблицу пользователей.
- `000004_create_user_library` — создаёт таблицы личной библиотеки исполнителей и релизов.

Для каждой миграции предусмотрены файлы `up.sql` и `down.sql`.

## 4. SQL-запросы и sqlc

SQL-запросы приложения хранятся в `db/queries`. По ним генерируется типизированный Go-код с помощью `sqlc`, размещённый в `internal/database/sqlc`.

При изменении запросов необходимо обновить сгенерированный код командой проекта для запуска `sqlc`.

## 5. Текущие ограничения

Реализованы базовый музыкальный каталог, связи релизов с исполнителями, внешние идентификаторы, учётные записи и личная библиотека.

На уровне схемы пока не предусмотрены:
- оценки исполнителей и релизов;
- личные заметки;
- пользовательские подборки;
- настройки публичности подборок;
- сохранение чужих подборок;
- редакционные статьи и рецензии;
- интеграция с внешними музыкальными каталогами.

Новые сущности и изменения схемы добавляются отдельными миграциями по мере развития проекта.

## 6. Текущие ограничения

На текущем этапе реализована базовая модель музыкального каталога.

Пока отсутствуют:

* таблицы пользователей и профилей;
* личная музыкальная библиотека;
* оценки исполнителей и релизов;
* личные заметки;
* пользовательские коллекции;
* настройки публичности коллекций;
* сохранение чужих коллекций;
* редакционные статьи и рецензии;
* интеграция с MusicBrainz или другими внешними каталогами.

Эти сущности будут добавляться отдельными миграциями по мере реализации функциональности.

## 7. Принципы проектирования

При развитии схемы базы данных придерживаемся следующих принципов:

1. Миграции вместо ручного изменения схемы. Структура базы должна воспроизводиться на новом окружении.
2. SQL отдельно от бизнес-логики. Запросы хранятся в db/queries/, а доступ к данным реализуется через сгенерированный sqlc-код.
3. Внешние идентификаторы отдельно от основных сущностей. Это позволяет подключать новые источники данных без изменения основной модели.
4. Явные ограничения целостности. Первичные и внешние ключи, уникальные ограничения и CHECK помогают предотвращать некорректные данные.
5. Без преждевременной интеграции. Сначала формируем надёжную внутреннюю модель каталога, затем добавляем внешние источники.
