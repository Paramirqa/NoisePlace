# NoisePlace API

## 1. Общая информация

- **Base URL:** `http://localhost:8080`
- **Формат данных:** JSON
- **Кодировка:** UTF-8
- **Версия API:** `v1`

Защищённые endpoints требуют JWT access token в заголовке:

```http
Authorization: Bearer <access_token>
```

Access token выдаётся при успешной авторизации и действует 24 часа.

Ошибки возвращаются в формате:

```json
{
  "error": "error description"
}
```

### GET `/readyz`

Проверяет готовность приложения к работе.

**Успешный ответ:** `200 OK`

## 3. Аутентификация

### POST `/api/v1/auth/register`

Регистрирует пользователя.

**Тело запроса:**

```json
{
  "username": "music_user",
  "email": "user@example.com",
  "password": "a-strong-password"
}
```

**Требования к полям:**

- `username` — от 3 до 32 символов; допустимы латинские буквы, цифры и `_`.
- `email` — корректный адрес электронной почты, не более 254 символов. Перед сохранением приводится к нижнему регистру.
- `password` — от 12 до 128 байт UTF-8.

Неизвестные поля в JSON не допускаются. Тело запроса должно содержать ровно один JSON-объект.

**Успешный ответ:** `201 Created`

Возвращает созданного пользователя. Пароль и его хеш в ответе не возвращаются.

**Возможные ошибки:**

- `400 Bad Request` — некорректный JSON или данные не прошли валидацию.
- `409 Conflict` — имя пользователя или email уже заняты.
- `500 Internal Server Error` — ошибка регистрации.

### POST `/api/v1/auth/login`

Авторизует пользователя по email и паролю.

**Тело запроса:**

```json
{
  "email": "user@example.com",
  "password": "a-strong-password"
}
```

Email перед поиском приводится к нижнему регистру.

**Успешный ответ:** `200 OK`

```json
{
  "access_token": "<jwt>",
  "token_type": "Bearer",
  "expires_in": 86400
}
```

`expires_in` — срок действия токена в секундах.

**Возможные ошибки:**

- `400 Bad Request` — некорректный JSON или отсутствуют email и пароль.
- `401 Unauthorized` — неверные учетные данные.
- `500 Internal Server Error` — внутренняя ошибка авторизации.

## 4. Пользователи

### GET `/api/v1/users/me`

Возвращает профиль текущего пользователя.

**Авторизация:** обязательна.

**Успешный ответ:** `200 OK`

```json
{
  "id": 1,
  "username": "music_user",
  "email": "user@example.com",
  "created_at": "2026-10-23T12:00:00Z",
  "updated_at": "2026-10-23T12:00:00Z"
}
```

Временные метки приведены как пример; фактический формат определяется сериализацией `time.Time`.

**Возможные ошибки:**

- `401 Unauthorized` — отсутствует или недействителен токен.
- `404 Not Found` — пользователь не найден.
- `500 Internal Server Error` — ошибка получения профиля.

## 5. Исполнители

### POST `/api/v1/artists`

Создаёт исполнителя.

**Тело запроса:**

```json
{
  "name": "ATL",
  "normalized_name": "atl",
  "sort_name": "ATL",
  "description": "Описание исполнителя",
  "image_url": null
}
```

`name` — обязательное поле. `normalized_name` может формироваться автоматически, если не передан. Остальные необязательные поля допускают отсутствие значения или `null` в соответствии с обработчиком.

**Успешный ответ:** `201 Created`.

Возвращает созданного исполнителя.

### GET `/api/v1/artists/{id}`

Возвращает исполнителя по ID.

**Успешный ответ:** `200 OK`.

**Возможные ошибки:**

- `400 Bad Request` — некорректный ID.
- `404 Not Found` — исполнитель не найден.

### GET `/api/v1/artists?query={query}&limit={limit}&offset={offset}`

Ищет исполнителей.

**Параметры:**

- `query` — поисковая строка.
- `limit` — количество результатов; точные ограничения задаются обработчиком.
- `offset` — смещение; точные ограничения задаются обработчиком.

Результаты сортируются по `normalized_name`, затем по `id`. Поиск через `LIKE` чувствителен к регистру в соответствии с текущей реализацией.

**Успешный ответ:** `200 OK` с массивом исполнителей. Если совпадений нет, возвращается пустой массив.

### PUT `/api/v1/artists/{id}`

Обновляет данные исполнителя.

Тело запроса использует те же поля, что и создание исполнителя.

**Успешный ответ:** `200 OK`.

**Возможные ошибки:**

- `400 Bad Request` — некорректный ID или данные запроса.
- `404 Not Found` — исполнитель не найден.
- `500 Internal Server Error` — ошибка обновления.

## 6. Релизы

### POST `/api/v1/releases`

Создаёт релиз.

**Тело запроса:**

```json
{
  "title": "Название релиза",
  "release_type": "album",
  "release_date": "2026-10-23",
  "description": "Описание релиза",
  "cover_url": null,
  "artists": [
    {
      "artist_id": 1,
      "role": "primary",
      "position": 0
    }
  ]
}
```

**Поля:**

- `title` — название релиза, обязательное.
- `release_type` — тип релиза, обязательный.
- `release_date` — дата в формате `YYYY-MM-DD`, необязательная.
- `description` — описание, необязательное.
- `cover_url` — ссылка на обложку, необязательная.
- `artists` — массив связанных исполнителей; при создании требуется хотя бы один исполнитель.

Допустимые значения `release_type`:

- `album`
- `ep`
- `single`
- `compilation`
- `mixtape`
- `live`
- `other`

У исполнителя допустимы роли `primary`, `featured`, `producer`. Если `role` не передана, используется `primary`. Если `position` не передан, используется индекс элемента в массиве, начиная с нуля. Позиция не может быть отрицательной. Среди связанных исполнителей должен быть хотя бы один с ролью `primary`.

**Успешный ответ:** `201 Created`. Возвращает релиз вместе со связанными исполнителями.

**Возможные ошибки:** `400 Bad Request` при ошибке валидации, `409 Conflict` при конфликте ограничений уникальности, `500 Internal Server Error` при внутренней ошибке.

### GET `/api/v1/releases`

Ищет релизы.

**Параметры запроса:**

- `query` — обязательная поисковая строка.
- `limit` — количество результатов, по умолчанию `20`, допустимый диапазон `1–100`.
- `offset` — смещение, по умолчанию `0`, должно быть неотрицательным.

**Успешный ответ:** `200 OK` с массивом релизов. Если совпадений нет, возвращается пустой массив.

### GET `/api/v1/releases/{id}`

Возвращает релиз по ID вместе со связанными исполнителями.

**Успешный ответ:** `200 OK`.

**Возможные ошибки:** `400 Bad Request` при некорректном ID, `404 Not Found`, если релиз не найден.

### PUT `/api/v1/releases/{id}`

Обновляет данные релиза.

**Тело запроса:**

```json
{
  "title": "Новое название",
  "release_type": "album",
  "release_date": "2026-10-23",
  "description": "Новое описание",
  "cover_url": null
}
```

`title` и `release_type` обязательны. `release_date`, `description` и `cover_url` необязательны. Этот endpoint обновляет поля релиза; для изменения связей с исполнителями используются отдельные endpoints.

**Успешный ответ:** `200 OK`.

**Возможные ошибки:** `400 Bad Request`, `404 Not Found`, `500 Internal Server Error`.

### DELETE `/api/v1/releases/{id}`

Удаляет релиз.

**Успешный ответ:** `204 No Content`.

**Возможные ошибки:** `400 Bad Request` при некорректном ID, `404 Not Found`, если релиз не найден.

## 7. Связи релизов с исполнителями

### GET `/api/v1/releases/{id}/artists`

Возвращает исполнителей, связанных с релизом.

**Успешный ответ:** `200 OK` с массивом исполнителей и информацией об их связях с релизом.

**Возможные ошибки:** `400 Bad Request`, `404 Not Found`, если релиз не найден.

### POST `/api/v1/releases/{id}/artists`

Добавляет связь между релизом и исполнителем.

**Тело запроса:**

```json
{
  "artist_id": 2,
  "role": "featured",
  "position": 1
}
```

`artist_id` обязателен. `role` по умолчанию равен `primary`. `position` по умолчанию равен `0`. Позиция должна быть неотрицательной.

**Успешный ответ:** `201 Created` с актуальным списком исполнителей релиза.

**Возможные ошибки:**

- `400 Bad Request` — некорректные данные.
- `404 Not Found` — релиз или исполнитель не найден.
- `409 Conflict` — связь нарушает ограничение уникальности.

### PUT `/api/v1/releases/{id}/artists/{artist_id}`

Обновляет роль и позицию исполнителя в релизе.

**Тело запроса:**

```json
{
  "role": "featured",
  "position": 1
}
```

Оба поля обязательны. Допустимые роли: `primary`, `featured`, `producer`. Позиция должна быть неотрицательной.

**Успешный ответ:** `200 OK` с актуальным списком исполнителей релиза.

**Возможные ошибки:** `400 Bad Request`, `404 Not Found`, `409 Conflict`.

### DELETE `/api/v1/releases/{id}/artists/{artist_id}`

Удаляет связь между релизом и исполнителем, не удаляя сами сущности.

**Успешный ответ:** `204 No Content`.

**Возможные ошибки:** `400 Bad Request`, `404 Not Found`, если релиз, исполнитель или связь не найдены.

## 8. Личная библиотека

Все endpoints этого раздела требуют авторизации. Библиотека принадлежит текущему пользователю, определяемому по access token.

### POST `/api/v1/me/library/artists/{artistID}`

Добавляет исполнителя в библиотеку.

**Успешный ответ:** `204 No Content`.

Повторное добавление уже существующего исполнителя не приводит к ошибке.

**Возможные ошибки:**

- `400 Bad Request` — некорректный ID.
- `401 Unauthorized` — отсутствует или недействителен токен.
- `404 Not Found` — исполнитель не найден.
- `500 Internal Server Error` — ошибка добавления.

### DELETE `/api/v1/me/library/artists/{artistID}`

Удаляет исполнителя из библиотеки.

**Успешный ответ:** `204 No Content`.

**Возможные ошибки:** `400 Bad Request`, `401 Unauthorized`, `404 Not Found`, если исполнитель отсутствует в библиотеке.

### GET `/api/v1/me/library/artists`

Возвращает исполнителей в личной библиотеке.

**Успешный ответ:** `200 OK` с массивом объектов, содержащих поля исполнителя и `added_at` — время добавления в библиотеку.

Если библиотека пуста, возвращается `[]`.

### POST `/api/v1/me/library/releases/{releaseID}`

Добавляет релиз в библиотеку.

**Успешный ответ:** `204 No Content`.

Повторное добавление уже существующего релиза не приводит к ошибке.

**Возможные ошибки:** `400 Bad Request`, `401 Unauthorized`, `404 Not Found`, `500 Internal Server Error`.

### DELETE `/api/v1/me/library/releases/{releaseID}`

Удаляет релиз из библиотеки.

**Успешный ответ:** `204 No Content`.

**Возможные ошибки:** `400 Bad Request`, `401 Unauthorized`, `404 Not Found`, если релиз отсутствует в библиотеке.

### GET `/api/v1/me/library/releases`

Возвращает релизы в личной библиотеке.

**Успешный ответ:** `200 OK` с массивом объектов, содержащих поля релиза и `added_at` — время добавления в библиотеку.

Если библиотека пуста, возвращается `[]`.

## 9. Общие правила обработки ошибок

Ошибки возвращаются в формате:

```json
{
  "error": "error description"
}
```

Основные HTTP-коды:

| Код | Значение |
|---|---|
| `200 OK` | Запрос выполнен успешно |
| `201 Created` | Ресурс создан |
| `204 No Content` | Операция выполнена без тела ответа |
| `400 Bad Request` | Некорректный запрос или данные не прошли валидацию |
| `401 Unauthorized` | Требуется авторизация или учетные данные недействительны |
| `404 Not Found` | Ресурс не найден |
| `409 Conflict` | Конфликт уникальности или состояния данных |
| `500 Internal Server Error` | Внутренняя ошибка сервера |

## 10. Текущие возможности API

API поддерживает:

- регистрацию и авторизацию пользователей;
- получение профиля текущего пользователя;
- работу с каталогом исполнителей и релизов;
- управление связями исполнителей с релизами;
- личную библиотеку исполнителей и релизов;
- пользовательские оценки исполнителей и релизов;
- получение публичной статистики оценок;
- создание, получение, обновление и удаление личных заметок.

Полный перечень endpoints, параметры запросов, схемы данных и HTTP-коды ответов описаны в спецификации `openapi.yaml`.

При расхождении краткого описания в этом документе со спецификацией ориентируйтесь на актуальную реализацию API и OpenAPI.

## 11. Просмотр и проверка документации OpenAPI

Полная спецификация API находится в файле [`openapi.yaml`](./openapi.yaml). Она использует формат OpenAPI 3.1.0.

### Swagger UI

Для просмотра интерактивной документации необходим Docker.

Из директории `docs` выполни:

```bash
docker run --rm \
  -p 8081:8080 \
  -e SWAGGER_JSON=/spec/openapi.yaml \
  -v "$PWD/openapi.yaml:/spec/openapi.yaml:ro" \
  swaggerapi/swagger-ui
```

После запуска открой в браузере:

http://localhost:8081

### Проверка спецификации

Для проверки корректности OpenAPI-файла с помощью Redocly CLI без установки Node.js выполни из директории `docs`:

```bash
docker run --rm \
  -v "$PWD:/spec" \
  -w /spec \
  node:22-alpine \
  npx --yes @redocly/cli lint openapi.yaml
```

Команда проверяет структуру и правила OpenAPI. Предупреждения Redocly не обязательно означают ошибки спецификации.
