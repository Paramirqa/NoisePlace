Структура базы данных

1. Общая информация

Проект использует PostgreSQL для хранения музыкального каталога.

Работа с базой данных организована следующим образом:

* PostgreSQL — основная СУБД.
* golang-migrate — управление миграциями схемы базы данных.
* sqlc — генерация Go-кода на основе SQL-запросов.
* pgx/v5 — подключение к PostgreSQL и выполнение запросов.

Основные директории:

db/
├── migrations/       # SQL-миграции
└── queries/          # SQL-запросы для sqlc
internal/
└── database/
    ├── postgres.go   # Подключение к PostgreSQL
    └── sqlc/         # Сгенерированный sqlc-код

Важно: файлы в internal/database/sqlc/ генерируются автоматически. Изменения в запросах нужно вносить в db/queries/, а изменения схемы — через миграции.

2. Таблицы

2.1. artists

Хранит информацию об исполнителях.

Поле	Тип	Ограничения	Описание
id	BIGINT	Primary Key, Identity	Уникальный идентификатор
name	TEXT	NOT NULL, не пустое	Отображаемое имя исполнителя
normalized_name	TEXT	NOT NULL, не пустое	Нормализованное имя для поиска
sort_name	TEXT	NULL допустим	Имя для сортировки
description	TEXT	NULL допустим	Описание исполнителя
image_url	TEXT	NULL допустим	Ссылка на изображение
created_at	TIMESTAMPTZ	NOT NULL	Дата создания записи
updated_at	TIMESTAMPTZ	NOT NULL	Дата последнего обновления

Индексы

* Индекс по normalized_name для поиска исполнителей.

Особенности

* name — оригинальное отображаемое имя.
* normalized_name используется для поиска и сравнения имён.
* Приложение формирует normalized_name путём удаления пробелов по краям и приведения строки к нижнему регистру.
* База данных проверяет, что name и normalized_name не пустые.
* Автоматическое обновление updated_at при изменении записи пока не реализовано на уровне БД: значение обновляется приложением при соответствующих операциях.

⸻

2.2. releases

Хранит информацию о музыкальных релизах: альбомах, EP, синглах и других типах релизов.

Поле	Тип	Ограничения	Описание
id	BIGINT	Primary Key, Identity	Уникальный идентификатор релиза
title	TEXT	NOT NULL, не пустое	Название релиза
release_type	TEXT	NOT NULL, ограниченный набор значений	Тип релиза
release_date	DATE	NULL допустим	Дата выхода
description	TEXT	NULL допустим	Описание релиза
cover_url	TEXT	NULL допустим	Ссылка на обложку
created_at	TIMESTAMPTZ	NOT NULL	Дата создания записи
updated_at	TIMESTAMPTZ	NOT NULL	Дата последнего обновления

Допустимые значения release_type:

* album
* ep
* single
* compilation
* mixtape
* live
* other

Индексы

* Индекс по title.
* Индекс по release_date.

Особенности

* Дата выхода может отсутствовать, если она неизвестна.
* Тип релиза проверяется ограничением CHECK.
* В текущей модели нет отдельной таблицы жанров.

⸻

2.3. release_artists

Связывает релизы с исполнителями.

Таблица нужна, потому что у одного релиза может быть несколько исполнителей, а один исполнитель может участвовать во множестве релизов.

Поле	Тип	Ограничения	Описание
release_id	BIGINT	Foreign Key, часть Primary Key	Идентификатор релиза
artist_id	BIGINT	Foreign Key, часть Primary Key	Идентификатор исполнителя
role	TEXT	NOT NULL, значение по умолчанию primary	Роль исполнителя
position	INTEGER	NOT NULL, значение по умолчанию 0, неотрицательное	Порядок исполнителя в списке

Допустимые значения role:

* primary — основной исполнитель;
* featured — приглашённый исполнитель;
* producer — продюсер.

Ограничения и индексы

* Составной первичный ключ: (release_id, artist_id, role).
* release_id ссылается на releases.id.
* artist_id ссылается на artists.id.
* Индекс (artist_id, release_id) для получения релизов исполнителя.
* position не может быть отрицательным.

Поведение при удалении

* При удалении релиза его связи с исполнителями удаляются автоматически (ON DELETE CASCADE).
* Удалить исполнителя, у которого есть связи с релизами, нельзя (ON DELETE RESTRICT).

Пример

Для альбома, в котором участвуют два исполнителя:

release_id	artist_id	role	position
1	10	primary	0
1	11	featured	1

Таким образом, состав исполнителей хранится отдельно от основной информации о релизе.

⸻

2.4. artist_external_ids

Хранит внешние идентификаторы исполнителей.

Таблица подготовлена для будущей интеграции с внешними музыкальными каталогами. Сейчас внешняя синхронизация не реализована.

Поле	Тип	Ограничения	Описание
id	BIGINT	Primary Key, Identity	Идентификатор записи
artist_id	BIGINT	Foreign Key, NOT NULL	Исполнитель
source	TEXT	NOT NULL, не пустое	Источник идентификатора
external_id	TEXT	NOT NULL, не пустое	Идентификатор во внешней системе
created_at	TIMESTAMPTZ	NOT NULL	Дата создания записи

Ограничения

* Уникальная пара (source, external_id).
* Уникальная пара (artist_id, source).
* При удалении исполнителя его внешние идентификаторы удаляются автоматически (ON DELETE CASCADE).

Уникальность (artist_id, source) означает, что одному исполнителю можно назначить не более одного идентификатора от каждого источника.

⸻

2.5. release_external_ids

Хранит внешние идентификаторы релизов.

Структура аналогична artist_external_ids.

Поле	Тип	Ограничения	Описание
id	BIGINT	Primary Key, Identity	Идентификатор записи
release_id	BIGINT	Foreign Key, NOT NULL	Релиз
source	TEXT	NOT NULL, не пустое	Источник идентификатора
external_id	TEXT	NOT NULL, не пустое	Идентификатор во внешней системе
created_at	TIMESTAMPTZ	NOT NULL	Дата создания записи

Ограничения

* Уникальная пара (source, external_id).
* Уникальная пара (release_id, source).
* При удалении релиза его внешние идентификаторы удаляются автоматически (ON DELETE CASCADE).

⸻

3. Связи между таблицами

Текущая структура каталога:

artists
  │
  ├── artist_external_ids
  │
  └── release_artists
           │
           └── releases
                  │
                  └── release_external_ids

Связь между artists и releases — многие ко многим через release_artists.

Это позволяет поддерживать:

* релизы нескольких основных исполнителей;
* приглашённых исполнителей;
* продюсеров;
* получение списка релизов конкретного исполнителя;
* получение списка исполнителей конкретного релиза.

4. Миграции

Миграции находятся в db/migrations/.

Текущая начальная миграция:

db/migrations/
├── 000001_init.up.sql
└── 000001_init.down.sql

* *.up.sql — создаёт или изменяет структуру базы данных.
* *.down.sql — отменяет соответствующие изменения.

Правила работы с миграциями

1. Если миграция ещё не применялась, её можно корректировать в процессе разработки.
2. Если миграция уже применена, для дальнейших изменений следует создавать новую миграцию.
3. Не стоит переписывать историю применённых миграций: это может привести к расхождению схем между окружениями.
4. Каждая новая миграция должна иметь следующий порядковый номер.

Пример:

000002_add_artist_fields.up.sql
000002_add_artist_fields.down.sql

Запуск миграций

В проекте миграции выполняются через сервис migrate, настроенный в Docker Compose.

Для запуска сервиса:

docker compose run --rm migrate

Перед запуском проверь, что контейнеры и переменные окружения настроены согласно конфигурации проекта.

Важно: откат миграций может привести к потере данных. Перед выполнением down-миграций в окружении с нужными данными следует убедиться, что существует резервная копия.

⸻

5. SQL-запросы и sqlc

Исходные SQL-запросы находятся в db/queries/.

db/queries/
├── artists.sql
├── releases.sql
├── release_artists.sql
└── external_ids.sql

sqlc генерирует Go-код в:

internal/database/sqlc/

Основные операции с каталогом:

* создание исполнителя;
* получение исполнителя по ID;
* поиск исполнителей;
* обновление исполнителя;
* создание релиза;
* получение релиза;
* поиск релизов;
* обновление релиза;
* связывание релиза с исполнителем;
* получение исполнителей релиза;
* получение релизов исполнителя;
* добавление и поиск внешних идентификаторов.

Генерация кода

После изменения SQL-запросов или схемы базы данных:

sqlc generate

Для проверки SQL-конфигурации:

sqlc compile

Затем запусти тесты:

go test ./...

Сгенерированные файлы не следует редактировать вручную: при следующем запуске sqlc generate изменения будут перезаписаны.

6. Текущие ограничения

На текущем этапе реализована базовая модель музыкального каталога.

Пока отсутствуют:

* таблицы пользователей и профилей;
* личная музыкальная библиотека;
* оценки исполнителей и релизов;
* личные заметки;
* пользовательские коллекции;
* настройки публичности коллекций;
* сохранение чужих коллекций;
* редакционные статьи и рецензии;
* интеграция с MusicBrainz или другими внешними каталогами.

Эти сущности будут добавляться отдельными миграциями по мере реализации функциональности.

⸻

7. Принципы проектирования

При развитии схемы базы данных придерживаемся следующих принципов:

1. Миграции вместо ручного изменения схемы. Структура базы должна воспроизводиться на новом окружении.
2. SQL отдельно от бизнес-логики. Запросы хранятся в db/queries/, а доступ к данным реализуется через сгенерированный sqlc-код.
3. Внешние идентификаторы отдельно от основных сущностей. Это позволяет подключать новые источники данных без изменения основной модели.
4. Явные ограничения целостности. Первичные и внешние ключи, уникальные ограничения и CHECK помогают предотвращать некорректные данные.
5. Без преждевременной интеграции. Сначала формируем надёжную внутреннюю модель каталога, затем добавляем внешние источники.
