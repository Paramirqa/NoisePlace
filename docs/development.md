# Руководство разработчика NoisePlace

В этом документе описаны локальный запуск NoisePlace, работа с базой данных, генерация SQL-кода, тестирование и рекомендуемый рабочий процесс.

## 1. Требования

Для разработки используются:

- Go — backend и бизнес-логика.
- Docker Desktop и Docker Compose — запуск приложения и PostgreSQL.
- PostgreSQL — хранение данных.
- golang-migrate — управление миграциями базы данных.
- sqlc — генерация Go-кода из SQL-запросов.

Проверь доступность инструментов:

```bash
go version
docker --version
docker compose version
sqlc version
```

Убедись, что Docker Desktop запущен.

## 2. Запуск проекта

Команды выполняются из корневой директории репозитория.

Сборка образов и запуск сервисов:

```bash
docker compose up -d --build
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

Посмотреть логи всех сервисов:

```bash
docker compose logs -f
```

Посмотреть логи отдельного сервиса:

```bash
docker compose logs -f <service>
```

Вместо `<service>` укажи фактическое имя сервиса из `compose.yaml`.

## 3. Пересборка backend

Если изменился Go-код и необходимо проверить его в контейнере, пересобери только backend-сервис:

```bash
docker compose up -d --build --no-deps <backend-service>
```

Замени `<backend-service>` именем сервиса из `compose.yaml`.

Параметр `--no-deps` не запускает зависимости автоматически. Команда пересоздаёт контейнер backend с использованием нового образа, если это необходимо. Данные PostgreSQL в существующем volume при этом не удаляются.

Если изменился только Go-код и достаточно проверить его локально, сначала можно выполнить тесты и сборку без пересборки контейнеров.

## 4. Остановка и запуск контейнеров

Остановить работающие сервисы, сохранив контейнеры:

```bash
docker compose stop
```

Запустить остановленные контейнеры:

```bash
docker compose start
```

Перезапустить отдельный сервис без пересборки образа:

```bash
docker compose restart <service>
```

Остановить и удалить контейнеры и сеть проекта:

```bash
docker compose down
```

По умолчанию `docker compose down` не удаляет именованные volumes. Не используй `docker compose down -v`, если не планируешь удалить volumes: это может привести к потере данных PostgreSQL.

## 5. Работа с миграциями

Файлы миграций находятся в:

```text
db/migrations/
```

Каждое изменение схемы базы данных должно оформляться новой миграцией:

1. Создай новую миграцию со следующим номером.
2. Опиши изменение в файле `.up.sql`.
3. Опиши обратное изменение в соответствующем `.down.sql`.
4. Примени миграцию.
5. Обнови сгенерированный SQL-код.
6. Запусти тесты.

Не изменяй миграции, которые уже были применены в других окружениях. Для новых изменений создавай следующую миграцию.

В проекте предусмотрены цели Makefile для работы с миграциями. Перед использованием проверь доступные цели и их реализацию в `Makefile`:

```bash
make help
```

Если цель `help` не определена, открой `Makefile` и используй фактически объявленные цели `migrate-up` и `migrate-down`.

Перед откатом миграции убедись, что понимаешь, какие данные и объекты схемы будут удалены.

## 6. Генерация кода sqlc

Исходные SQL-запросы хранятся в:

```text
db/queries/
```

Конфигурация sqlc:

```text
sqlc.yaml
```

После изменения SQL-запросов или схемы базы данных выполни:

```bash
sqlc generate
```

Для проверки SQL-конфигурации:

```bash
sqlc compile
```

Сгенерированный Go-код находится в:

```text
internal/database/sqlc/
```

Не редактируй сгенерированные файлы вручную. Изменяй исходные SQL-запросы или схему, затем запускай генерацию повторно.

## 7. Тестирование и проверка кода

Запустить все Go-тесты:

```bash
go test ./...
```

Запустить тесты с подробным выводом:

```bash
go test -v ./...
```

Проверить статические ошибки:

```bash
go vet ./...
```

Проверить сборку пакетов:

```bash
go build ./...
```

После изменений Go-кода рекомендуется выполнить:

```bash
go test ./...
go vet ./...
go build ./...
```

Для форматирования Go-кода используй `gofmt` для изменённых файлов либо соответствующую цель из `Makefile`. Перед коммитом проверь `git diff`, чтобы убедиться, что форматирование не затронуло посторонние изменения.

### Интеграционные тесты

В проекте предусмотрена отдельная конфигурация Docker Compose для тестовой базы данных:

```text
compose.test.yaml
```

Запускай интеграционные тесты через соответствующую цель Makefile, если она настроена:

```bash
make test-integration
```

Перед запуском проверь реализацию этой цели: она должна использовать тестовую конфигурацию и тестовую базу данных, а не рабочую базу разработки.

## 8. Проверка HTTP API

Проверить доступность приложения:

```bash
curl -i http://localhost:8080/healthz
```

Проверить готовность приложения:

```bash
curl -i http://localhost:8080/readyz
```

Эти команды предполагают, что backend опубликован на порту `8080` хост-машины. Если в `compose.yaml` указан другой порт, используй его.

Ожидаемый ответ `/healthz`:

```json
{
  "status": "ok"
}
```

Ожидаемый ответ `/readyz` при успешной проверке готовности:

```json
{
  "status": "ready"
}
```

Описание остальных HTTP-маршрутов, форматов запросов и ответов находится в [документации API](api.md).

## 12. Рекомендуемый рабочий процесс

### При изменении Go-кода

1. Внеси изменения.
2. Запусти `go test ./...`.
3. Выполни `go vet ./...`.
4. Проверь сборку командой `go build ./...`.
5. Если требуется проверить работу в контейнере, пересобери backend.
6. Проверь `git diff` и зафиксируй изменения.

### При изменении SQL-запросов

1. Измени файл в `db/queries/`.
2. Выполни `sqlc generate`.
3. Запусти тесты.
4. Проверь сборку.
5. Если требуется, проверь работу API в контейнере.

### При изменении схемы базы данных

1. Создай новую миграцию.
2. Примени миграцию в нужном окружении.
3. Выполни `sqlc generate`.
4. Запусти тесты.
5. Проверь работу API.
6. Убедись, что новая миграция и сгенерированный код включены в коммит.
